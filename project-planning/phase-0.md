# Phase 0 — Foundation

## Objective

Produce a **runnable monorepo** with the data layer, local infrastructure, and application skeletons in place — but **zero feature code**. No chat endpoints, no LLM providers, no ingestion pipeline. Just the ground floor that every later phase will build on, designed once so we never have to rewrite it.

End state of Phase 0:

- `pnpm install` succeeds at the repo root
- `docker compose up -d` brings up healthy Postgres 16 and Redis 7 containers
- `pnpm --filter @olives/api prisma migrate dev` applies one migration that creates all 8 tables from `AGENT.md §3`
- `pnpm dev` starts `apps/api` on `:3001` and `apps/web` on `:3000` with hot reload
- `curl http://localhost:3001/health/live` returns `{"status":"ok"}`
- `curl http://localhost:3001/health/ready` returns `{"status":"ok","checks":{"database":"ok"}}`
- `http://localhost:3000` renders a placeholder homepage with a shadcn `Button` to prove Tailwind + shadcn are wired
- Both apps import a Zod schema from `packages/types` to prove the workspace linking works

Phase 0 ships **no business logic.** It only proves that every tool we will rely on for the rest of the project works together. Anything we discover broken here is far cheaper to fix now than after Phase 1 layers chat code on top.

## Locked Decisions Inherited Into Phase 0

These were confirmed with the user before this plan was written and apply to every step below:

- **Auth scope:** single-user / no auth. No NextAuth, no sessions in v1. Ingestion endpoint (Phase 2) will be protected by a static API key from `.env`. A `users` table still exists in the schema with one seed row so future auth is a code change, not a migration.
- **LLM providers in v1:** Anthropic only. Provider abstraction interface exists from Phase 1, but only the Anthropic adapter is implemented. OpenAI lands in Phase 3.
- **SDK location:** in-process module at `apps/api/src/sdk/inference-logger/`. No separate `packages/sdk-*`. Internal chat traffic calls the logger directly; the ingestion HTTP endpoint exists for external producers but is not used by our own chat flow.
- **Phase 0 scope:** infra + schema + skeletons, no features. All 8 tables land in one migration even though several (`ingestion_logs`, `inference_events`, `queue_jobs`, `provider_configs`) won't be written to until Phase 2/3. One migration is easier to review as a single data model than four scattered ones.

None. Phase 0 is the first phase and starts from an empty repo.

### Step 3 — Local infrastructure: Postgres + Redis

**Description:** A `docker-compose.yml` that brings up Postgres 16 and Redis 7 with persistent named volumes and healthchecks. App containers (`api`, `worker`, `web`) are deliberately **not** included in Phase 0 — those land in Phase 3's deployment hardening. In Phase 0 the apps run on the host via `pnpm dev` against containerized data services. This is the lowest-friction local DX and matches how a small team actually works day-to-day.

**Files created:**

- `/docker-compose.yml`
- `/.env.example` (root)

**Key content:**

`docker-compose.yml`:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    container_name: olives-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-olives}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-olives}
      POSTGRES_DB: ${POSTGRES_DB:-olives}
    ports:
      - "${POSTGRES_PORT:-5432}:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-olives} -d ${POSTGRES_DB:-olives}"]
      interval: 5s
      timeout: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    container_name: olives-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "${REDIS_PORT:-6379}:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:
  postgres_data:
  redis_data:
```

**Tradeoff note:** Redis AOF persistence is on (`--appendonly yes`). Strictly speaking, BullMQ workloads are tolerant of Redis restarts because failed jobs simply re-enter retry queues — AOF is mild over-engineering for v1. We're keeping it because the cost is negligible and it spares us from re-debugging "where did my dead-letter jobs go" after `docker compose down -v`. If disk pressure becomes a problem we can switch to RDB snapshots.

`/.env.example` (root) — variables that apply to multiple workspaces or to compose:

```env

POSTGRES_USER=olives
POSTGRES_PASSWORD=olives
POSTGRES_DB=olives
POSTGRES_PORT=5432

# Redis
REDIS_PORT=6379
```

App-specific `.env.example` files (`apps/api/.env.example`, `apps/web/.env.example`) are written in their respective bootstrap steps.

`apps/api/src/config/env.ts` — runs once at boot, parses with the shared schema, throws loud and early on missing config:

```typescript
import { apiEnvSchema, type ApiEnv } from '@olives/types/env/api';

export function loadEnv(): ApiEnv {
  const parsed = apiEnvSchema.safeParse(process.env);
  if (!parsed.success) {
    const issues = parsed.error.issues.map((i) => `${i.path.join('.')}: ${i.message}`).join('\n');
    throw new Error(`Invalid environment configuration:\n${issues}`);
  }
  return parsed.data;
}
```

No casts. The parsed result is `ApiEnv` because `safeParse` narrows on `success === true`.

`apps/api/src/config/config.module.ts` — exposes a typed `EnvService` via DI so feature modules consume `EnvService.get('DATABASE_URL')` rather than reading `process.env` themselves.

```typescript
import { Global, Module } from '@nestjs/common';
import { loadEnv } from './env';
import type { ApiEnv } from '@olives/types/env/api';

@Global()
@Module({
  providers: [
    {
      provide: 'ENV',
      useFactory: (): ApiEnv => loadEnv(),
    },
    {
      provide: EnvService,
      useFactory: (env: ApiEnv) => new EnvService(env),
      inject: ['ENV'],
    },
  ],
  exports: [EnvService],
})
export class ConfigModule {}

export class EnvService {
  constructor(private readonly env: ApiEnv) {}
  get<K extends keyof ApiEnv>(key: K): ApiEnv[K] {
    return this.env[key];
  }
}
```

Note: generic `get<K>` returns `ApiEnv[K]` without any cast. Type safety is end-to-end.

```typescript
import 'reflect-metadata';
```

### Step 7 — Prisma: schema + first migration

**Description:** Author the complete `schema.prisma` covering all 8 tables from `AGENT.md §3`, generate the Prisma client, and apply the first migration named `init`. After this step the database structurally matches the design doc and is ready for Phase 1+ feature code to write to it.

**Files created:**

- `apps/api/prisma/schema.prisma`
- `apps/api/prisma/migrations/<timestamp>_init/migration.sql` (generated)
- `apps/api/src/prisma/prisma.module.ts`
- `apps/api/src/prisma/prisma.service.ts`

**Files changed:**

- `apps/api/package.json` — add `@prisma/client` runtime dep, `prisma` dev dep
- `apps/api/src/app.module.ts` — import `PrismaModule`

**Prisma deps to install at this step:**

- runtime: `@prisma/client@^6.0.0`
- dev: `prisma@^6.0.0`

**Schema rationale:**

- Use Prisma `enum` types (which map to Postgres `enum` types) for status fields rather than free-form `varchar`. AGENT.md §3 lists the allowed values explicitly — pinning them in the schema gives type-safe Prisma client output with zero runtime checks. Cost: adding a new status requires a migration. Worth it.
- All IDs are UUIDs generated client-side via `@default(uuid())`. No need for `pgcrypto` extension.
- Every table has `created_at` (`@default(now())`) and `updated_at` (`@updatedAt`).
- Snake_case column names via `@map`, camelCase TypeScript names. Standard Prisma convention.
- All indexes from AGENT.md §3 are reproduced verbatim.

**Full `schema.prisma`:**

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

// ─── Enums ────────────────────────────────────────────────────────────────────

enum ConversationStatus {
  active
  completed
  cancelled
  archived
}

enum MessageRole {
  system
  user
  assistant
  tool
}

enum MessageStatus {
  completed
  streaming
  cancelled
```

**Note on the unique constraint for `ingestion_logs(source, source_event_id)`:** AGENT.md says this should be unique *only where `source_event_id` is not null*. Prisma can't express a partial unique index in `schema.prisma` directly. Two acceptable approaches:

1. Declare `@@unique([source, sourceEventId])` in Prisma and just keep `sourceEventId` nullable (Postgres treats `NULL`s as distinct so this works — multiple rows with `NULL sourceEventId` are allowed, which is exactly the partial-unique behavior we want).
2. Use a `migration.sql` patch to add `CREATE UNIQUE INDEX ... WHERE source_event_id IS NOT NULL`.

We'll go with option (1). Postgres NULL semantics give us partial-unique behavior for free with the simpler Prisma declaration. The migration SQL Prisma generates will read `UNIQUE NULLS DISTINCT` (Postgres 15+ default), which is what we want.

### Step 8 — `/health/live` and `/health/ready` endpoints

**Description:** Two endpoints that prove the api process is alive and that its critical dependencies (Postgres) are reachable. Redis is in compose but no app code talks to it yet (BullMQ wires in Phase 2), so `/health/ready` checks DB only in Phase 0 and gets a Redis check added in Phase 2.

**Why two endpoints?** Standard practice for container orchestrators: `liveness` says "the process hasn't deadlocked, don't restart me"; `readiness` says "I can serve traffic right now". Conflating them causes restart loops when an upstream dependency hiccups.

**Files created:**

- `apps/api/src/modules/health/health.module.ts`
- `apps/api/src/modules/health/health.controller.ts`

**Key content:**

```typescript
// health.controller.ts
import { Controller, Get } from '@nestjs/common';
import { PrismaService } from '../../prisma/prisma.service';

@Controller('health')
export class HealthController {
  constructor(private readonly prisma: PrismaService) {}

  @Get('live')
  live(): { status: 'ok' } {
    return { status: 'ok' };
  }

  @Get('ready')
  async ready(): Promise<{ status: 'ok' | 'degraded'; checks: { database: 'ok' | 'fail' } }> {
    const database = await this.prisma
      .$queryRaw`SELECT 1`
      .then(() => 'ok' as const)
      .catch(() => 'fail' as const);
    return {
      status: database === 'ok' ? 'ok' : 'degraded',
      checks: { database },
    };
  }
}
```

No `as` casts. The `'ok' as const` / `'fail' as const` pattern is `as const` (literal-type narrowing), which is a TypeScript type assertion form. Per the strict no-casting rule, we cannot use this. Rewrite:

```typescript
@Get('ready')
async ready(): Promise<{ status: 'ok' | 'degraded'; checks: { database: 'ok' | 'fail' } }> {
  let database: 'ok' | 'fail' = 'fail';
  try {
    await this.prisma.$queryRaw`SELECT 1`;
    database = 'ok';
  } catch {
    database = 'fail';
  }
  return {
    status: database === 'ok' ? 'ok' : 'degraded',
    checks: { database },
  };
}
```

Explicit variable typing replaces the literal cast. Same behavior, zero casts.

**Decision: skip `@nestjs/terminus`.** Terminus is the canonical Nest health-check library but it pulls in a non-trivial dep and an opinionated indicator system for what amounts to ~15 lines of code. We'll add it in Phase 2 if Redis + queue health probes warrant it.

## Implementation Notes

Technical decisions and tradeoffs to keep in mind while executing the steps above.

**Why a modular monolith and not microservices from day one.** Phase 0 deliberately ships one backend (`apps/api`) and one frontend (`apps/web`). A separate `worker` process for BullMQ shows up in Phase 2 — but it's the same NestJS codebase started with a different entry point, not a separate deployment artifact. Microservice boundaries are easy to add later; they're nearly impossible to remove. `AGENT.md §1` makes this the foundational design decision.

**Why all 8 tables now and not phase-by-phase migrations.** Reviewability. A single `init` migration that reflects the entire intended data model is far easier to evaluate than four migrations scattered across phases. The cost (some tables sit empty until Phase 2/3) is trivial. If we discover in Phase 1 that a schema choice was wrong, we'll create a follow-up migration; we won't rewrite history.

**Why Prisma enums instead of `varchar` + check constraints.** Type-safe Prisma client output, Postgres-level validation, zero runtime cost. AGENT.md §3 explicitly enumerates the allowed values for every status field — that information would be lost if we used `varchar`. The downside (adding a new status requires a migration) is acceptable because status sets are deliberately stable.

**Why `nestjs-pino` instead of the default Nest logger.** Structured JSON logs by default, request-context propagation via async-hooks, zero ceremony to add `request_id` to every log line. The default Nest console logger is fine for prototyping; it's a liability in production where we need to grep by `inference_request_id` across thousands of log lines.

**Why no `@nestjs/terminus` in Phase 0.** It's ~15 lines of custom indicator code now versus a dependency that brings opinionated patterns we don't yet need. We add it in Phase 2 when Redis + queue health checks justify the abstraction.

**Why no Husky / lint-staged in Phase 0.** Adds friction to the first-time setup. Lint and typecheck are enforced in CI (Phase 3); local pre-commit hooks are nice-to-have, not required.

**Why no testing framework configured in Phase 0.** No feature code exists to test. Phase 1 introduces Vitest (or Jest if NestJS opinions tip the balance) when the first chat-service unit test is needed. Setting up a test framework now would mean configuring something we haven't validated we need.

**Why `pnpm` over `npm` or `yarn`.** Workspaces are first-class, disk-efficient (content-addressable store), and the resolver is strict — implicit `node_modules` access from non-declared deps fails fast, which catches integration bugs that npm would happily ignore. The user's `AGENT.md §6` already lists `pnpm-workspace.yaml`.

**Why Next.js 15 + React 19.** Both are stable as of the project start date (2026-05). React Server Components are the right model for the chat UI's data-fetching shape. We avoid Turbopack in dev for Phase 0 to keep the dev-server stack on the more battle-tested SWC+Webpack path.

**Why Tailwind 4 over Tailwind 3.** Tailwind 4 ships stable in 2025, has a faster engine, and uses CSS-first config. shadcn-ui supports v4. No reason to start a 2026 project on v3.

**Why `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.** Both flags catch the kind of bug the user's no-casting rule prevents from being papered over. With casts banned, the type system actually has to be tight enough to express intent. These flags make it so.

**Why no `as` casts anywhere.** User rule from `~/.claude/CLAUDE.md`. Enforced via ESLint's `@typescript-eslint/consistent-type-assertions: { assertionStyle: "never" }`. The price is occasional verbose narrowing (e.g., the Step 8 health-check rewrite); the reward is that every type in the codebase is honest.

**Why every Zod schema lives in `packages/types`.** User rule from `~/.claude/CLAUDE.md`. This is enforced socially in code review for Phase 0; in Phase 3 we can add a lint rule that bans `import { z }` outside of `packages/types/**`.

**What Phase 0 explicitly does NOT do:**

- No chat module, no conversation module, no inference module, no ingestion module, no dashboard module
- No BullMQ wiring, no worker process
- No PII redaction, no provider adapters
- No CI workflow (GitHub Actions lands in Phase 3)
- No Dockerfiles for `api`/`web`/`worker` (Phase 3)
- No production deployment story (Phase 3)
- No automated tests beyond `typecheck` + `lint`

Anything in that list that creeps into Phase 0 is scope creep and should be pushed to its owning phase.

## Handoff Context

What Phase 1 inherits from Phase 0:

**Workspace topology.** Two apps (`apps/api`, `apps/web`) plus one shared package (`packages/types`). Phase 1 adds feature modules under `apps/api/src/modules/` and route segments under `apps/web/src/app/`. No new top-level workspaces should be needed until the SDK is extracted (which the locked decision says will not happen in v1).

**Data model.** Every table that the system needs is already in the database. Phase 1 only needs to **write to and read from** existing tables — `users`, `conversations`, `messages`, `inference_requests`. It does not need to author new migrations unless a Phase 1 feature reveals a column we missed (we should flag this loudly in `phase-1.md` blockers if it happens).

**Config + logging contracts.** `EnvService` is the only sanctioned way to read environment variables in `apps/api`. Pino is the only logger. Phase 1 must follow both rules — feature modules should inject `EnvService` and the Nest pino `Logger`, never reach into `process.env` or `console.log` directly.

**Zod schemas live in `packages/types`.** This is non-negotiable for the rest of the project. When Phase 1 introduces request/response DTOs for `POST /chat/conversations`, those Zod schemas go in `packages/types/src/chat/`, not in `apps/api`. The api uses them via DTO validation pipes; the web app uses them for typed `fetch` wrappers.

**No-cast rule is lint-enforced.** Phase 1 code that tries `value as Foo` will fail lint. If a type narrowing problem is hard, the answer is a better type, a Zod parse at the boundary, or a generic — never a cast.

**Provider abstraction shape.** Phase 1 will introduce the `LlmProvider` interface at `apps/api/src/providers/llm/provider.interface.ts` per `AGENT.md §6`. Only the Anthropic adapter is implemented in Phase 1. OpenAI adapter is deferred to Phase 3 per the locked decision.

**SDK shape.** Phase 1 will introduce `apps/api/src/sdk/inference-logger/` as in-process module. No HTTP self-loopback for internal chat traffic. The ingestion HTTP endpoint (Phase 2) is for external producers only.
